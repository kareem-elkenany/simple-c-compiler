# Parser Line Number Bug Fix Explanation

This document briefly outlines the difference between how the `simple-c-compiler` parser previously handled tokens and how the recent fix improves syntax error line reporting.

## The Previous Parser Behavior

Previously, the parser used a strict Regular Expression (`re.match(r'^\((\d+),\s*(.*?),\s*(.*?)\)$', line)`) to read lines from `tokens.txt` generated by the scanner.

**The Bug:**
The scanner's output for an end-of-line token lacked a leading line number (it output `(\n, EOL)` instead of something like `(1, \n, EOL)`). Because this output did not start with a digit, it completely failed to match the parser's regex.

As a result, the parser **silently dropped all `EOL` tokens**.

**The Consequence:**
Without `EOL` tokens, the parser saw the code as one continuous line. If you left a statement incomplete on line 1, the parser wouldn't stop at the end of the line. Instead, it would jump directly into the first token of line 2 to find the "missing" piece of your statement. 

When that token didn't fit, the parser would raise a `SyntaxError` pointing to **Line 2**, leading to confusion because the actual mistake was on Line 1.

*Example Scenario:*
```text
1: x is 
2: show x
```
*Old Error:* `Unexpected token PRINT (show) at line 2`

## The Fixed Parser Behavior

The recent fix adds an explicit check in `parser.py` (inside the `read_tokens` function) to catch `EOL` tokens regardless of whether they have a line number. 

**The Fix:**
```python
# Match EOL token in both forms: (\n, EOL) or (1, \n, EOL)
if ", EOL)" in line:
    match_line = re.match(r'^\((\d+),', line)
    line_no = int(match_line.group(1)) if match_line else (tokens[-1][2] if tokens else 1)
    tokens.append(("EOL", r"\n", line_no))
    continue
```
This safely catches the `EOL` token. If the token is missing a line number from the scanner, the parser simply copies the line number from the most recently parsed token.

**The Result:**
Because `EOL` tokens are now successfully added to the parser's stream, the parser knows exactly where lines end. If a statement is left incomplete, the parser will immediately hit the `EOL` token and throw an error right there.

*Example Scenario:*
```text
1: x is 
2: show x
```
*New Error:* `Unexpected token EOL at line 1`

By restoring the `EOL` tokens to the stream, the parser now stops precisely at the broken line, successfully providing accurate line-number-based syntax error reporting!
